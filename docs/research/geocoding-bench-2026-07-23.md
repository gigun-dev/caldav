## 総評

### (a) 解決率(該当0件・エラーを除く)

- GSI: 16/18
- Google Places Text Search (New): 18/18
- Apple Maps Server API: 17/18

GSI は住所文字列に対する部分一致検索であり、POI 名(施設名・店舗名)には非対応。たとえば「東京駅」で検索すると『東』の字を含む無関係な住所(北海道札幌市東区など)が先頭にヒットする挙動を確認した(RFC 準拠実装とは無関係な外部 API の仕様上の制約として記録)。GSI は住所(番地)クエリでは高精度に解決する一方、POI・チェーン店・自然文には原理的に弱い。

### (b) POI での強さ

- Google: 有名 POI・チェーン店(スターバックス 渋谷 / ドン・キホーテ 名古屋)いずれも高精度に解決し、上位候補が該当エリア内の実在店舗に一致。`raw_count` も複数返り曖昧解消の材料になる。
- Apple: 有名 POI(東京駅・東京ドーム・大阪城・岐阜市役所など)は高精度。ただし `品川の叙々苑`(必須クエリ)はsearch・geocode いずれも 0 件で解決できず、`岐阜駅前のスタバ` は該当エリア外(蔵前)の無関係な地点を返した。`スターバックス 渋谷` も店舗名までは特定できず「東京都渋谷区」という地域名止まりで返る傾向が見られ、チェーン店の曖昧クエリに弱い。
- GSI: POI 名を扱えないため非該当(住所検索専用)。

### (c) 住所での強さ

- GSI: 番地・丁目レベルの住所クエリ(`東京都渋谷区道玄坂2-1-1` `岐阜県岐阜市橋本町1丁目10-1` `千代田区丸の内1丁目`)はいずれも高精度に解決し、3者中もっとも一貫して安定していた。
- Google: 住所クエリも良好に解決するが、返る `formattedAddress` は必ずしも入力と同じ粒度に整形されない(例: `道玄坂２丁目１−１` のように名称欄に住所断片が入るケースがある)。
- Apple: 番地レベルの住所クエリで無関係な POI(ドンキ、岐阜駅)を返すケースがあり、住所としての解決精度は3者中もっとも不安定だった(`limit=3` の中でも番地と無関係な結果が上位に出る)。

### (d) タイトル・住所・geo の3点セット(structuredLocation)としての使いやすさ

- Google が最も structuredLocation(タイトル=displayName / 住所=formattedAddress / geo=location)にそのまま使える形式で一貫して返る。フィールドマスクで必要項目だけを指定でき、レスポンスも整形済み。
- Apple も `name` `formattedAddressLines` `coordinate` の3点セットを持つが、POI の曖昧クエリで名称が地域名に丸められたり(`蔵前` `南品川` など)、`品川の叙々苑` のように0件で3点セットを得られないケースがあり、Google ほど安定しない。
- GSI は名称フィールドが存在しないため単独では structuredLocation を構成できず、住所+geo の2点セットに限られる(タイトルは呼び出し側でクエリ文字列や他プロバイダの名称と合成する必要がある)。

**総合結論**: iOS の「場所」フィールド(structuredLocation)を狙うなら Google Places Text Search (New) が最有力(解決率・POI強度・3点セットの安定性すべてで優位)。GSI は住所クエリの高精度な裏取り・座標の相互検証(2km 乖離フラグ)用の補助プロバイダとして併用する価値がある。Apple はトークン交換自体は成功したが、POI 曖昧クエリでの取りこぼし(`品川の叙々苑` 不通)と住所クエリでの誤答が目立ち、現状では主力プロバイダとしては採用しづらい。
